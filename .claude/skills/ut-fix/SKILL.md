# 평가 결과 반영하기

## 시작하며 설명할 것 (처음 한 번만)

> 사용성 평가에서 찾은 문제를 하나씩 고쳐서 서비스를 완성해요. 고칠 때마다 "무엇이 문제였고, 무엇을 근거로, 어떻게 바꿨는지"를 남겨요. 이 기록이 보고서에서 가장 설득력 있는 부분이 돼요.

**한 번 부를 때 문제는 하나만 고쳐요.**

## 준비

- `ut/findings.md` 를 읽으세요. 없으면 `/ut-result` 부터 하자고 하고 멈추세요.
- "이번에 고친다" 이고 상태가 "할 일"인 문제 중 고칠 순서가 가장 빠른 것을 고르세요. 학생이 번호를 말했으면 그 문제.
- 그 문제의 화면 `section` 만 `design/prototype.html` 에서 읽으세요. 스타일은 `design/style-guide.md` 를 따르세요.

## 1. 문제 다시 보기

- 문제, 근거(참가자가 한 말이나 클로드 UT 기록), 고른 개선안을 짧게 보여주세요.
- 개선안이 아직 정해지지 않았으면 후보 2개를 장단점과 함께 보여주고 팀이 고르게 하세요.
- 고치면 다른 화면이나 플로우에 영향이 있는지 미리 알려주세요 (예: 버튼 이름을 바꾸면 다른 화면의 같은 버튼도 바꿔야 함).

## 2. 고치기

- 그 화면 `section` 만 고치세요. 같은 이름의 버튼이나 공통 부품을 바꿨으면, 같은 것이 쓰인 다른 화면도 같이 맞추세요.
- 화면 흐름이 바뀌면(화면 추가, 순서 변경) `flow/flow.md` 와 `flow/flow.html` 도 고치세요.
- 기능이 바뀌면 기획서의 해당 부분을 고칠지 팀에게 묻고, 고치면 변경 기록에 남기세요.
- 브라우저에서 다시 눌러 보게 하세요 (윈도우 `start "" design\prototype.html`, 맥 `open design/prototype.html`).

## 3. 기록

- `ut/findings.md` 에서 그 문제의 상태를 "고침"으로 바꾸세요.
- `ut/changes.md` 에 한 덩어리씩 쌓으세요:

```
## F1: (문제 한 줄)
- 근거: (참가자가 한 말이나 클로드 UT 기록)
- 바꾸기 전: (어떤 모습이었는지)
- 바꾼 뒤: (어떻게 바꿨는지)
- 고친 파일: design/prototype.html (화면 ID), flow/flow.md
- 이유: (왜 이 개선안을 골랐는지)
```

## 4. 확인 (원하면)

- 고친 과제를 클로드가 같은 퍼소나로 다시 짧게 따라가 보자고 제안하세요. 이번에는 그 과제 하나만, 고친 화면 근처만 보세요. 결과를 changes.md 의 그 덩어리 아래에 "다시 확인:" 으로 한 줄 남기세요.

## 마무리

- 저장하고 GitHub에 올리라고 알려주세요.
- 남은 "할 일" 문제를 알려주세요. "다음 문제는 새 세션에서 `/ut-fix` 로 하면 사용량을 아낄 수 있어요."
- 다 고쳤으면 `/design 점검` 으로 전체를 한 번 보고, `/report` 로 한 장 요약을 새로 만들고, `/share` 로 공유하자고 하세요.
